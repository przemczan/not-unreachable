# Security review

This is the security review of NotUnreachable against its own
[threat model](../design/threat-model.md) (T1–T15) and OWASP ASVS 5.0 levels 1
and 2. It found 12 issues and fixed all of them, each with a regression test.
What is left is in the threat model's
[residual risk register](../design/threat-model.md#residual-risk-register).

## Version reviewed

- **Base:** commit `d43d262` on `main` ("feat: add Linux install script,
  release tarballs and hardened systemd units").
- **Date:** 2026-11-25.
- **Fixes:** made in the Security review Task (Task
  f1f3aa6d-0023-4448-bbe0-cefb832cb17b) and landed as its one commit.

## Scope

In scope: everything that ships or runs the app.

- `apps/server`: every module in [domain.md](../design/domain.md), the HTTP
  layer (headers, CSRF, rate limits, logging) and the CLI.
- `apps/web`: the SPA, both interfaces and the public share page.
- `packages/contracts`: the route table (access, `recentSignIn`, `safe`).
- `deploy/`: the install script, the CLI wrapper, the systemd units, the polkit
  rule, the mount helper and the Caddy and nginx examples.
- The release build (`scripts/release/`), the CI and Release workflows and the
  lockfile.

Out of scope: the operator's host beyond what the installer sets up, the
reverse proxy's own code, the SSO providers and the SMTP server.

## Method

The review ran in four static areas and one dynamic pass. Each area checked its
threat-model rows and ASVS chapters against the code, ran the tests behind each
row, and added or strengthened a test where one was missing or weak.

| Area                     | Threat-model rows                                                            | ASVS chapters             |
| ------------------------ | ---------------------------------------------------------------------------- | ------------------------- |
| A. Authentication        | T1, T2, T9, T10, T11 (sign-in rows), the six sign-in model checks SIGNIN.1–6 | V6, V7, V9, V10           |
| B. Files and share links | T4.4–5, T5.1, T5.2, T5.4, T5.5, T7, T8, T11 (share links, uploads)           | V2, V5, V8                |
| C. Web platform          | T3, T4.1–3, T4.6, T6.1, T6.3–5, T12, T13 (headers), T15                      | V1, V3, V4, V11, V14, V16 |
| D. Host and supply chain | T5.3, T6.2, T6.6, T13 (supply chain), T14                                    | V12, V13, V15             |
| Z. Dynamic               | –                                                                            | –                         |

The dynamic pass ran OWASP ZAP and manual `curl` probes against a production
build behind Caddy (see [Dynamic checks](#dynamic-checks)).

Fix policy: every Critical, High and Medium finding is fixed here; a Low one is
fixed when small, otherwise it goes in the register. **Every fix has a
regression test in the normal test suite, and each one was shown to fail
without its fix** (run before the fix, or with the fix reverted).

Row ids: `T<n>.<k>` is the k-th row of threat T<n>'s table. For T5, T5.1 is the
row "The steps above". For T11, the rows are those of the limit table. For T13,
T13.1 is the **Headers** paragraph and T13.2–T13.10 are the supply-chain
bullets in order. SIGNIN.1–6 are the sign-in model checks of the Task's plan.

CVSS 4.0 base scores come from the reviewers' notes. Scores marked
_estimated_ were worked out by hand, not with a calculator.

## Dynamic checks

**Target.** `pnpm build`, then the server with `NODE_ENV=production`,
`PUBLIC_ORIGIN=https://localhost:8443`, a fresh data folder, a random master
key and `TRUSTED_PROXIES=127.0.0.1`, behind `deploy/proxy/Caddyfile` as shipped
(host changed to `localhost:8443`, with `tls internal`). The admin was created
through the real flow over Caddy: `setup-link`, setup, sign-in, authenticator
enrolment, recovery codes. Then a local resource (with a file `docs/xss.html`
holding `<script>alert(1)</script>`), a file share link, a password-protected
folder share link, the home root and an invitation, whose real tokens the scans
and probes used.

**Baseline scan.** 20 public URLs (pages, the share page with real tokens, the
invitation page with a real and a bogus token, public API routes) and the
traditional spider; passive rules only; default limits.

**Authenticated scan.** The admin's active session cookie, `X-NU-Request: 1`
and our `Origin` on every request; sign-out and session routes left out; seeds:
the public URLs, 11 SPA routes, 24 admin and account `GET` routes with real ids,
then a second pass with JSON bodies through ZAP's proxy (profile, resource
check, share link, folder, invitation, share unlock, limits). Default active
policy, minus rules for other databases and platforms. The per-IP limits were
raised for this scan only, as the e2e fixtures do, and put back before the
manual probes. 6 289 requests; no 5xx answer and no error in the server log;
the admin session was still active at the end.
